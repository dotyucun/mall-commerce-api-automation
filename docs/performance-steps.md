# 阶梯读取负载实验

## 目的与边界

旧的 `performance` 命令保留 20 用户轻量基线。新增 `performance-steps` 用于观察固定测试环境下，增加虚拟用户后成功吞吐、响应时间和失败率如何变化。被测 mall 源码不修改。

这不是生产流量模型，也不预设一定存在拐点。工作负载仍为单专用会员、独立 HTTP 会话、固定商品与关键词、搜索/详情/购物车权重 3:2:1。结果只适用于这个热点读取场景，不代表大规模商品、多账号、复杂购物车或写入链路的容量。

## 执行步骤

1. 核对固定 SUT commit、Compose 服务、API 健康和专用测试数据基线。确认没有功能回归同时运行，不停止不属于本项目的容器。
2. 运行 `smoke`，只验证采样、鉴权、请求校验和报告流程，不把其数字作为容量结果。
3. 运行 `explore`：等待 0.1 秒，用户数 10/20/40/80，每档所有用户登录成功后预热 30 秒，稳态 60 秒。档位之间冷却 10 秒，各档使用独立工作进程。
4. 如果资源安全、未触发停止条件且仍未观察到拐点，可显式增加 160/320 等档位；不自动无上限增加负载。
5. 对临界档位和相邻对照档运行 `confirm`：各预热 30 秒，稳态 300 秒，重复两轮。探索只能提出候选结论，不能代替确认。
6. 降压后检查服务恢复及数据基线，审阅原始 JSON/CSV、HTML、资源和数据库采样，再更新 README。

```powershell
.\scripts\mall-test.ps1 performance-steps -PerformanceProfile smoke
.\scripts\mall-test.ps1 performance-steps -PerformanceProfile explore
.\scripts\mall-test.ps1 performance-steps -PerformanceProfile explore -PerformanceUsers 160,320
.\scripts\mall-test.ps1 performance-steps -PerformanceProfile confirm -PerformanceUsers 40,80
```

配置在 `performance/steps.yaml`。输出写入 `reports/locust/steps/<UTC时间>/`，不会覆盖历史基线。Python 运行器返回 2 表示触发停止条件；统一 PowerShell 入口会显示该退出码并以非零退出，不能包装成成功。非零的工作进程退出码属于执行错误。

阶梯实验明确使用 `http://127.0.0.1:8085`。本机 `localhost` 的 IPv6/IPv4 回退曾导致每次新建连接约 2.1 秒，不能把传输路径问题归因为商城容量不足。旧基线入口和项目默认地址不改动，实验目标地址在结果元数据中保留。

## 统计口径

- 稳态窗口使用单调时钟控制；同时记录 UTC 起止时间。RPS 的分母为该阶段明确的测量窗口秒数，不是整个进程配置时长。
- 仅汇总在稳态窗口内发起并完成的请求。预热中发起、窗口内才完成的请求不计入；窗口内发起、结束后完成的请求单独记录为尾部请求，尾部失败也会阻止通过。
- 请求起点与完成分类都使用单调时钟；额外核对 `started_requests`（窗口内发起数）等于稳态完成数、尾部完成数和 `incomplete_requests`（未完成数）之和。停止时仍未完成的请求不能静默丢弃，有未完成请求即标记本档证据不完整。
- 每档重新建立 Locust 统计对象，输出各接口及聚合的请求数、失败数、RPS、成功 RPS、平均耗时、P95、P99。不会平均不同档位的 P95。
- HTTP、业务码、关键数据校验沿用基线。登录只用于准备 Token，不计入读取指标。
- 原始 `history.csv` 中 P95 是该阶段窗口内截至采样时的累计分位数，不是相邻两次采样间的分位数。

## 资源与判定

每阶段保留 Docker 容器 CPU、内存、I/O 等原始数据，压测进程 CPU/RSS、宿主机内存，以及 MySQL 连接数、运行线程、慢查询计数、锁等待计数和缓冲池读取计数。数据库累计计数应比较同阶段的差值，不能直接把最终值当成本轮新增数量。

Docker/操作系统/数据库采集在独立进程执行，避免阻塞负载进程的事件循环。该隔离不会消除同机资源竞争，因此仍需记录其他运行的容器与宿主机限制。

压测进程 CPU 百分比按 psutil 的单核口径，可能超过 100%；容器 CPU 也可能因多核超过 100%。不得把两者当作同一比例或使用整机平均 CPU 掩盖单个压测进程饱和。

停止条件包括：聚合或任一读取接口失败率达到 1%、P95 达到 1000ms、没有请求、接口样本缺失、用户初始化或运行异常、资源证据缺失、压测进程稳态 CPU 中位数达到 90%。这是本实验门槛，不是生产 SLA。触发发生器 CPU 门槛只能说明当前发生器可能限制负载，不能据此宣称商城容量上限。

候选拐点使用公开的探索规则：用户数增加至少 50%，成功 RPS 增长不足 20%，同时聚合 P95 增加至少 50%。这只是筛选线索；必须重复验证并结合接口分项、资源和数据库数据分析。仅 CPU 高不能证明具体代码或数据库是根因。

## 实测结果

2026-10-16 已完成 10/20/40/80/160 用户探索、80 用户两轮各 5 分钟确认及 160 用户独立复测。高档位先触发发生器 CPU 门槛，未确认服务端容量上限；第二轮确认保留了 1 次传输失败，未伪装成零失败。具体数字、限制、原始证据和复核命令见 [本轮实验记录](performance-20261016.md)。
